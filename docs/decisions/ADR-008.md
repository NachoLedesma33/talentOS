# ADR-008 — Skills locales del proyecto como estándares del coding agent

Fecha: 2026-11-23
Estado: Aceptado

## Contexto

SDD 18 define Agent Skills de programación, distintos de los agentes de IA del producto, y fija su ubicación en `.opencode/skills/<skill-id>/SKILL.md` con frontmatter YAML `name` y `description`, nombres `kebab-case` y descripciones específicas para activación. La sección 18.1 enumera 15 skills esenciales (`software-architecture`, `product-requirements`, `frontend-engineering`, `python-fastapi`, `postgresql-data-modeling`, `ai-agent-engineering`, `langgraph-workflows`, `application-security`, `testing-quality`, `technical-documentation`, entre otras) y 18.2 seis complementarias. SDD 18.4 exige en cada una objetivo, activación, contexto TalentOS, procedimiento, convenciones, anti-patrones, comandos de validación, checklist y referencias, sin copiar documentación completa de frameworks. El roadmap Fase 0 las entrega como artefacto, con criterio de frontmatter válido y contenido accionable, y SDD 23 advierte del riesgo «skills inseguras», mitigado revisando contenido, scripts y permisos antes de adoptarlas.

## Decisión

Mantener las skills versionadas en el repositorio, en `.opencode/skills/`, como estándares operativos del coding agent para este proyecto, con un conjunto pequeño y adaptado a TalentOS; no instalar decenas de skills genéricas (SDD 18). Cada skill codifica límites concretos extraídos del SDD y `AGENTS.md`: monolito modular, `organization_id` derivado de la sesión, backend como autoridad, `LLMProvider` detrás de la capa de agentes, evidencias verificables, aprobación humana, modo mock y sin secretos ni datos personales reales. Se revisan autor, instrucciones, scripts, permisos y versión de cualquier skill externa antes de adoptarla, rechazando las que pidan secretos o desactiven checks (SDD 18.6). Las skills no sustituyen al SDD ni a los ADRs: referencian documentos del repositorio y se actualizan cuando cambia una convención o un criterio de aceptación. Las skills del producto (agentes LangGraph) siguen siendo código del backend, no skills del coding agent.

Esta decisión sostiene de forma indirecta los principios SDD 1.2 al convertir en reglas ejecutables la autoridad del backend, la trazabilidad y el modo demo; evita que cada agente de código reinterprete esos límites.

## Alternativas consideradas

- **Skills globales genéricas:** no capturan los límites de TalentOS (multi-tenancy, evidencias, aprobaciones) y derivan del SDD.
- **Adoptar skills externas sin revisión:** riesgo de scripts, permisos o instrucciones que desactiven validaciones (SDD 23 y 18.6).
- **Solo `AGENTS.md` o README extenso:** concentra todo en un documento que no se activa por tarea y se vuelve difícil de mantener.
- **Una única skill monolítica:** reduce la precisión de activación y mezcla frontend, persistencia, IA y despliegue en un mismo texto.

## Consecuencias

Positivas:

- Respuestas consistentes entre agentes de código y entre fases, con anti-patrones y comandos de validación explícitos.
- Onboarding más rápido: cada skill indica cuándo activarse y qué checklist cerrar.
- Los cambios de arquitectura se reflejan primero en ADRs y luego en skills, reduciendo deriva documental.

Negativas:

- Coste de mantenimiento: cada skill puede quedar obsoleta si el código o el SDD cambian sin actualizarla.
- Un frontmatter inválido o una descripción ambigua impide la activación correcta; hay que validarlo en Fase 0.
- Para tareas triviales, cargar skills añade ruido; por eso se prioriza un conjunto pequeño y disparadores específicos.
