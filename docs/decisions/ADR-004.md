# ADR-004 — Procesamiento asíncrono para documentos y agentes

Fecha: 2026-11-23
Estado: Aceptado

## Contexto

RNF-006 del SDD 5 exige que las tareas largas se ejecuten fuera del ciclo HTTP; RNF-007 y RNF-015 piden idempotencia y límites de tamaño, tipo y frecuencia. Extraer un CV, ejecutar un grafo de agentes, llamar a un proveedor LLM y enviar integraciones pueden superar el tiempo de una petición web. El SDD 8.3 define estados explícitos para documentos (`uploaded → queued → extracting → review_required → confirmed`) y ejecuciones de agente (`pending → running → waiting_approval → completed`, con `failed`, `cancelled`, `timed_out`). El diagrama SDD 6.3 sitúa `Redis / Cola → Worker → LangGraph Workflows`; SDD 11.1 define el envelope de eventos con `organization_id` y `correlation_id`, y SDD 11.2 exige consumidores idempotentes, reintentos exponenciales acotados, dead-letter, timeouts, estado visible y reintento manual autorizado. SDD 11.3 obliga a responder rápido y procesar webhooks en background.

## Decisión

La API valida la solicitud, persiste el recurso con su estado inicial y encola un job con un identificador, el `organization_id` derivado de la sesión autorizada y el contexto mínimo; nunca serializa objetos ORM (SDD 6.4). Redis/Celery o alternativa equivalente transporta el trabajo; los workers ejecutan extracción, grafos LangGraph (ADR-006) y procesamiento de webhooks. Los consumidores son idempotentes; las escrituras usan idempotency key, los reintentos son exponenciales con máximo definido y los fallos terminan en dead-letter o registro diagnosticable con reintento manual con permisos. Se usa outbox transaccional cuando evento y transacción deben persistir juntos (SDD 11.2). Las transiciones se modelan con enums y el frontend consulta el estado; los logs y eventos propagan `correlation_id` (RNF-004). Las aprobaciones humanas dejan el job en `waiting_approval` y se reanudan mediante API (ADR-006).

Principios SDD 1.2 aplicados: «operaciones críticas idempotentes y auditables», «trazabilidad» y «backend como autoridad»; el worker hereda la autorización de la organización, no inventa permisos.

## Alternativas consideradas

- **Ejecución síncrona en el request:** expone timeouts, obliga al usuario a esperar y hace que un reintento duplique extracciones o mensajes; incumple RNF-006.
- **Hilos en proceso dentro de FastAPI:** se pierden al reiniciar, no ofrecen estado consultable ni reintento durable.
- **Solo polling periódico desde el frontend:** añade latencia, carga innecesaria y no sustituye la ejecución durable en worker.
- **Colas separadas por dominio desde el inicio:** duplicaría infraestructura y observabilidad sin evidencia; el monolito modular permite una cola compartida con contratos (ADR-001).

## Consecuencias

Positivas:

- HTTP responde rápido y la UI muestra estados reales de `queued`, `extracting`, `waiting_approval` o `failed`.
- Reintentos, cancelación, timeout y reanudación quedan determinados por contrato, no por improvisación.
- La traza `correlation_id` conecta API, worker, grafo y herramientas (SDD 15.1).

Negativas:

- Consistencia eventual: el cliente debe manejar estados pendientes y volver a consultar.
- Más infraestructura local (Redis, worker) y más casos de prueba: job duplicado, fallo de proveedor y cross-tenant.
- Depurar un flujo distribuido exige logs estructurados y eventos persistidos; sin ellos, el coste cognitivo sube.
