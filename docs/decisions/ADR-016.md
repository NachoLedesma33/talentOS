# ADR-016 — Adoptar shadcn/ui como capa visual compartida

Fecha: 2026-11-25
Estado: Aceptado

## Contexto

La Entrega A completó A1–A5: inventario, tokens, shell opt-in, estados de error y E2E. CI verde para `fa8e6d9`, `01732b3`, `7fd464a`, `4ba7ce4` y `2a8b56c`. Revisión responsive automatizada en `1440x900`/`390x844` y revisión en dispositivos reales hecha por el usuario el 2026-11-25: responsive OK, pero la UI se ve pelada por falta de estilo shadcn.

`TalentOS_UI_UX_IMPROVEMENT_PLAN.md` §10 define shadcn/ui como base del sistema de diseño y §22 exige componentes compartidos con shadcn/ui y tokens centralizados. ADR-014 difirió su adopción a una decisión propia porque el repositorio no tenía `components.json`, Radix ni shadcn. ADR-015 cubre solo E2E; no habilita dependencias de UI.

Stack real verificado: Next.js `16.4.6` App Router, React `19.3.1`, TypeScript `5.9.3` estricto, Tailwind CSS `3.4.19`, alias `@/* → ./src/*`, tokens en `apps/web/src/styles/tokens.css` mapeados en `apps/web/tailwind.config.ts`. Existe `apps/web/src/components/ui/Button.tsx` local de A3, sin dependencias nuevas.

Documentación oficial consultada vía Context7: el CLI `npx shadcn@latest init` prepara `components.json`, util `cn` y variables CSS; `cssVariables: true` genera tokens semánticos y no puede cambiarse después sin reinstalar componentes; la ruta `tailwind.config` debe indicarse en Tailwind v3; React 19 puede exigir `--force` o `--legacy-peer-deps`. Fuentes: https://ui.shadcn.com/docs/cli , https://ui.shadcn.com/docs/components-json , https://ui.shadcn.com/docs/react-19 , https://ui.shadcn.com/docs/installation/gatsby .

## Decisión

1. **Adoptar shadcn/ui como fuente de componentes compartidos.** Los componentes se copian al repositorio bajo `apps/web/src/components/ui/`; se personalizan con los tokens de `tokens.css`, sin convertir shadcn en una plantilla visual inmutable. No se adopta un template de página completo.
2. **Inicializar con configuración revisada, no por defecto ciego.** Ejecutar la inicialización desde `apps/web` y revisar el diff antes de aceptarlo. `components.json` debe apuntar a `tailwind.config.ts`, `src/app/globals.css`, alias `@/components`, `@/lib/utils` y `@/components/ui`. Usar `cssVariables: true` y estilo `default` para el primer lote; cualquier cambio de estilo requiere nueva evidencia visual.
3. **Conservar los tokens medidos como autoridad visual.** Los valores ya verificados (`--color-surface`, `--color-surface-muted`, `--color-text`, `--color-text-muted`, `--color-border: #7a8794`, `--color-accent`, `--color-focus`, `--color-on-accent`, `--color-success`, `--color-warning`) no se sustituyen por la paleta por defecto de shadcn. Las variables semánticas que genere el CLI se mapean a esos tokens; `--color-border-subtle` sigue siendo solo decorativo. Si el CLI reescribe `globals.css` o `tailwind.config.ts`, se revisa el diff antes de conservar cualquier cambio.
4. **Dependencias mínimas y justificadas.** Se permiten `class-variance-authority`, `clsx`, `tailwind-merge`, `lucide-react` y el primitivo Radix correspondiente a cada componente que se instale. Versiones quedan fijadas por `package-lock.json`. React 19: intentar instalación estándar; si aparece error de peer dependencies, repetir con `--legacy-peer-deps` y documentar el comando exacto. No añadir React Hook Form, Zod, TanStack Table ni Recharts sin caso de uso en la fase correspondiente.
5. **Migración incremental, sin duplicados.** Primer lote: configuración + `cn` + `Button` shadcn, migrando los imports de `LoginForm.tsx` y `DocumentUpload.tsx`. El `Button.tsx` local de A3 se retira solo después de que los tests y el build verifiquen la migración; borrarlo es una operación separada y requiere confirmación. Lotes siguientes: `Card`, `Input`, `Label`, `Table` y estados, uno por vez, con tests de accesibilidad y responsive.
6. **Límites intactos.** shadcn solo cambia presentación y primitivas accesibles. No modifica autorización, contratos `/api/v1`, reglas de negocio, persistencia, agentes ni decisiones de contratación. No habilita acciones externas automáticas ni introduce secretos.

## Alternativas consideradas

- **Mantener primitivas propias sin estilo:** evita dependencias, pero contradice §22 y deja la UI pelada que el usuario reportó en dispositivos reales.
- **Instalar Radix directamente:** da accesibilidad, pero obliga a reconstruir estilos, tokens y variantes que shadcn ya entrega como código auditable.
- **Aplicar un template visual completo de shadcn:** acelera el cambio, pero rompe rutas, shell opt-in y contraste medido; requiere ADR y revisión propia.
- **Migrar a Tailwind v4 en este lote:** no es necesario para instalar componentes con Tailwind v3 y ampliaría el riesgo fuera de la Entrega A.

## Consecuencias

Positivas:

- Componentes accesibles con estilo centralizado, editables en el repositorio.
- Cumple el criterio §22 sin delegar reglas de negocio ni autorización al frontend.
- Tokens medidos siguen siendo la única fuente de color; shadcn consume ese sistema.
- Migración por lotes pequeños con gates y evidencia verificable.

Negativas:

- Nuevas dependencias de UI y lockfile más grande; cada primitivo Radix exige revisión de compatibilidad con React 19.
- El diff de inicialización puede tocar `globals.css` y `tailwind.config.ts`; debe revisarse manualmente.
- Entrega A no se cierra hasta completar el estilo de los componentes compartidos y repetir gates, E2E y revisión responsive.
