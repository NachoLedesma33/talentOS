# ADR-003 — PostgreSQL como fuente de verdad

Fecha: 2026-11-23
Estado: Aceptado

## Contexto

El SDD 6.2 designa PostgreSQL para datos transaccionales y el SDD 8.1 define entidades con relaciones fuertes: `Organization`, `Membership`, `Job`, `JobVersion`, `Candidate`, `CandidateDocument`, `Extraction`, `Assessment`, `AssessmentCriterion`, `Evidence`, `AgentRun`, `Approval` y `AuditLog`. El SDD 8.2 exige UUID públicos, fechas UTC, `created_at`/`updated_at`, foreign keys y constraints únicos explícitos, índices por `organization_id`, estados y fechas, retención real en lugar de soft delete por defecto, metadatos de archivos en base de datos y secretos cifrados. RNF-013 pide migraciones versionadas y RNF-014 política de retención y eliminación. Las transiciones de estados (SDD 8.3) y el outbox transaccional (SDD 11.2) requieren atomicidad entre eventos y cambios de dominio.

## Decisión

Usar PostgreSQL como única fuente de verdad para entidades, estados, relaciones, evidencias, aprobaciones y auditoría. Modelar estados como enums con transiciones permitidas desde el backend (SDD 8.3), imponer integridad con foreign keys, constraints e índices por organización, y evolucionar el esquema solo con migraciones Alembic versionadas. Los documentos se guardan en storage privado compatible S3; PostgreSQL conserva `storage_key`, `mime_type`, `checksum` y estado (SDD 8.2). Redis se usa como broker/cache (SDD 6.2), nunca como fuente de verdad. El estado de proveedores externos y LLM se registra como metadato versionado, no como sustituto del registro local. La auditoría se escribe en la misma transacción que la operación cuando el SDD lo requiere (ADR-004), con política de backup y restauración probada.

Esto sostiene «backend como autoridad», «operaciones críticas idempotentes y auditables» y «trazabilidad de entradas, salidas, versiones de prompts y herramientas» (SDD 1.2).

## Alternativas consideradas

- **MongoDB u otro store documental:** flexibilidad para JSON de extracción, pero traslada a código las foreign keys, unicidad y transiciones atómicas que SDD 8.2 y 8.3 existen para garantizar.
- **SQLite como base principal:** útil para pruebas locales, insuficiente para API y workers concurrentes con multi-tenancy.
- **Redis como fuente de verdad:** velocidad, pero persistencia parcial y sin constraints relacionales ni consultas de auditoría fiables.
- **Solo object storage para resultados:** simplifica archivos, pero impide consultar evidencias, aprobaciones y trazas con integridad transaccional.

## Consecuencias

Positivas:

- Una sola transacción protege cambios de dominio, eventos outbox y auditoría.
- Constraints e índices hacen cumplir reglas cross-tenant y búsquedas frecuentes sin depender solo de código.
- Migraciones reproducibles y seed sintético permiten reiniciar la demo (SDD 22).

Negativas:

- Todo cambio de esquema exige migración revisada; los experimentos de IA no pueden crear campos ad hoc.
- Mapeo ORM y consultas complejas requieren supervisión de rendimiento (RNF-018).
- El escalado de escrituras puede necesitar particionado o réplicas más adelante; no se asume un free tier ilimitado (SDD 6.2).
