# ADR-005 — Adaptador LLM desacoplado (mock/remoto/local)

Fecha: 2026-11-23
Estado: Aceptado

## Contexto

RNF-016 del SDD 5 exige una arquitectura preparada para cambiar de proveedor LLM; la tabla de riesgos SDD 23 incluye «cambios de proveedor» y «costos de inferencia». SDD 6.4 establece que los proveedores LLM se encapsulan detrás de interfaces. SDD 9.6 define el puerto interno con `generate_structured_output()`, `generate_text()`, `health_check()` y `estimate_usage()` cuando el proveedor lo soporte, con adaptadores para proveedor remoto configurable, modelo local opcional y mock determinista. El mismo apartado advierte que el equipo puede no disponer de GPU dedicada, que la demo debe funcionar con mocks y que no se debe prometer inferencia local rápida sin medirla. SDD 14.3 prohíbe exponer secretos al contexto del modelo; SDD 16.2 exige que los tests no dependan de un proveedor pago.

## Decisión

Definir una interfaz interna `LLMProvider` con las cuatro operaciones de SDD 9.6 y tres adaptadores intercambiables: remoto configurable, modelo local liviano opcional y mock determinista (`LLM_PROVIDER=mock`). El dominio no conoce al proveedor: solo la capa de agentes invoca el puerto y valida las salidas con Pydantic antes de persistirlas (SDD 9.5). Modelo, endpoint, timeout, límites y parámetros se configuran por entorno; secretos solo variables de entorno o gestor (RNF-003). Cada llamada registra proveedor, versión de modelo, versión de prompt, consumo estimado cuando exista y `correlation_id`, sin volcar CV completo ni secretos en logs. Tests y demo usan el mock por defecto; cambiar de adaptador no modifica flujos, contratos ni esquemas de salida.

Esto materializa los principios SDD 1.2 «proveedores de IA intercambiables mediante una capa de abstracción» y «la aplicación debe poder ejecutarse en modo demo sin credenciales de servicios pagos», además de «trazabilidad» y «no inventar evidencia» mediante validación de esquemas y referencias.

## Alternativas consideradas

- **Llamadas directas al SDK en cada agente:** acopla el dominio al proveedor, imposibilita tests sin red y duplica timeouts, reintentos y métricas.
- **Usar solo la abstracción de un SDK propietario:** sigue siendo dependencia de un fabricante y no resuelve el mock determinista ni el modelo local.
- **Exigir GPU e inferencia local obligatoria:** contradice SDD 9.6 y excluye el entorno de desarrollo descrito.
- **Un protocolo distinto por agente:** multiplicaría adaptadores y haría imposible comparar versiones de prompts y modelos en Simulation Lab (roadmap Fase 11).

## Consecuencias

Positivas:

- Tests y demo reproducibles, sin credenciales pagas ni red; salidas deterministas para evaluaciones de regresión.
- Cambiar de proveedor reduce a configuración y un adaptador, sin tocar reglas de negocio.
- Consumo y latencia quedan medibles antes de prometer rendimiento (RNF-018).

Negativas:

- La interfaz común puede no exponer capacidades exclusivas de un proveedor; se resuelve con características opcionales detectadas en el adaptador.
- Capa adicional de mapeo y errores que mantener y probar.
- El mock puede ocultar diferencias reales de comportamiento; por eso las evaluaciones deben ejecutarse también con el proveedor configurado cuando haya autorización y presupuesto.
