# ADR-013 — Cifrado de configuración de integraciones y límite de adaptadores

Fecha: 2026-11-24
Estado: Aceptado

## Contexto

La Fase 9 del roadmap inicia el núcleo de integraciones: interfaz, ciclo de vida de credenciales y cifrado de configuración. SDD 8.1 define `Integration(id, organization_id, provider, encrypted_config_ref, status)`; SDD 8.2 exige cifrar secretos de integraciones y nunca guardar API keys en texto plano; SDD 14.1 exige secretos fuera del repositorio, cifrado en reposo y logs sin tokens; SDD 11.3 describe firma HMAC, secreto rotatorio y configuración por organización para webhooks. SDD 3.2 exige `organization_id` derivado de la sesión y filtrado en cada consulta.

Threat model mínimo: activos = secretos de proveedor, endpoints de webhook, metadatos de versión y borradores de correo; actores = owner/admin, miembro lector, usuario de otro tenant y proveedor externo; flujo = sesión autorizada → servicio → repositorio tenant-scoped → PostgreSQL → adaptador sandbox. Riesgos: fuga cross-tenant, lectura de secretos vía API o logs, escritura sin control de concurrencia y dependencia de crypto implementada a mano. Mitigaciones de esta unidad: UNIQUE `(organization_id, provider)`, filtro de tenant en repositorio y servicio, roles de escritura `owner|admin`, `expected_version` optimista, contratos Pydantic estrictos por proveedor, respuestas y auditoría sin config.

## Decisión

Usar `cryptography.fernet.Fernet` con una clave única por despliegue leída de `INTEGRATION_ENCRYPTION_KEY` (Fernet de 32 bytes en base64 url-safe, solo entorno/gestor). La base guarda únicamente `encrypted_config_ref` con el token y `key_id = sha256(clave_decodificada).hexdigest()[:12]` como identificador público para rotación futura. Sin clave o con clave inválida: `integration_key_missing`; token ilegible o clave equivocada: `integration_config_unreadable`. Ningún mensaje, log ni respuesta incluye clave, token, config ni secreto.

La configuración es esquemática y cerrada por proveedor: `email_sandbox` → `{sink: "local_log"}` (sin credencial), `webhook_outbound` → `{endpoint: HttpUrl, secret: str>=16}`, `webhook_inbound` → `{secret: str>=16, tolerance_seconds: 60..3600}`. No se inventan proveedores futuros. `IntegrationUpdateRequest` exige `expected_version` y cambia config o estado, nunca ambos; recifrar incrementa `config_version`. Auditoría: `integration.created` / `integration.updated` con IDs y acción, validada con `validate_safe_payload` y sin payload sensible.

`cryptography` es la única dependencia nueva: Fernet ofrece cifrado autenticado (AEAD), manejo de clave y serialización de token listos para uso, es mantenida y auditada, y evita implementar AES-GCM, derivación o comparación de tags en código propio. Se fija `>=44,<45`.

La rotación de clave, HMAC saliente/entrante, dedupe, reintentos de webhook y UI quedan fuera de esta unidad y se resolverán con los adaptadores de webhooks salientes (donde `key_id` permitirá aceptar la clave anterior durante una ventana documentada).

Para correo se mantiene un único proveedor `email_sandbox` con `sink=local_log`. El borrador `EmailDraft` persiste solo UUID opaco de candidato, plantilla cerrada, tema/CTA acotados y saneados, asunto generado por servidor, `body_hash` SHA-256, estados de aprobación/envío, actores y timestamps. Nunca se persiste correo, nombre, CV, cuerpo completo ni secreto; la unicidad `(organization_id, integration_id, candidate_id, template, topic, language, call_to_action)` hace idempotente la creación. El adaptador `EmailSender` recibe un `EmailMessage` ya saneado y devuelve una referencia `sandbox:<hash corto>` o un código de error estable; sin SMTP, red ni impresión de texto.

La aprobación es una decisión humana separada y no delegable en quien creó el borrador: `pending -> approved|rejected` con `decided_by != requested_by`. Aprobar no envía; el envío exige estado `approved`, integración activa del tenant y se ejecuta de forma explícita. Éxito marca `sent` con `sent_at`; fallo marca `failed` con `last_error_code` y contador de intentos. Auditoría y logs solo contienen IDs, acción/código y resultado, nunca asunto, cuerpo ni dato personal. No hay autoaprobación, tarea Celery ni decisión de contratación.

## Alternativas consideradas

- **AES-GCM propio con `hashlib`/`hmac`:** más control, pero obligaría a diseñar nonce, AAD, formato de token y manejo de errores; riesgo innecesario frente a Fernet.
- **Guardar secretos en variables de entorno por organización:** mezcla tenants en el proceso, no escala y no deja versión por configuración.
- **Guardar JSON en claro con permisos de base de datos:** contradice SDD 8.2 y 14.1; cualquier lector de la tabla vería secretos.
- **Almacén externo de secretos desde esta unidad:** añade infraestructura y latencia sin caso de uso en el alcance actual; la clave de cifrado ya vive en el gestor de secretos del despliegue.
- **Config libre (`dict[str, Any]`):** facilitaría proveedores futuros, pero permitiría campos arbitrarios y secretos en respuestas; se prefiere unión estricta por proveedor.

## Consecuencias

Positivas:

- Secretos cifrados en reposo y nunca expuestos por API, logs o auditoría.
- Aislamiento cross-tenant demostrable con dos organizaciones sintéticas.
- Escrituras con control optimista y unicidad por proveedor dentro del tenant.
- Una sola dependencia nueva, justificada y fijada.
- Borradores auditables sin PII ni cuerpo: hash verificable y aprobación ajena obligatoria antes de enviar.

Negativas:

- Cada despliegue debe gestionar una clave Fernet; sin ella las integraciones no operan (el arranque en modo mock no se bloquea).
- La rotación real de clave aún no existe; `key_id` se persiste preparado para ella.
- `config_version` se incrementa solo en la capa de servicio, no por trigger de base de datos.
- El envío es sandbox: no hay entrega real ni métricas de proveedor en esta fase.
